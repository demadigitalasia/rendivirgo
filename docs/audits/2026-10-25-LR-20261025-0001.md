**4. Temuan prioritas P1 — perlu ditangani sebelum uji operasional penuh/deploy**

**F01 — Pemeriksaan tipe frontend gagal. Status: terkonfirmasi.**

`npm run lint` di root menjalankan `tsc --noEmit` dan menghasilkan error. Yang langsung terkait Lapidary: `components/customer-lapidary.tsx:138` memiliki deklarasi properti `carrier`, `trackingNumber`, dan `trackingUrl` yang ditimpa oleh spread; `app/admin/(dashboard)/lapidary/content/page.tsx:86,416` mengunci tipe `imagePosition` terlalu sempit menjadi `center`, sehingga `left/right` ditolak TypeScript. Ada pula konflik tipe route hasil generator `.next` serta ekspor yang hilang pada modul Navigation.

Dampak: keberhasilan halaman pada dev server belum cukup menjadi bukti kesiapan release. Pemeriksaan tipe proyek belum lulus. Tidak ada klaim bahwa semua error ini berasal dari perubahan modal terakhir.

Rekomendasi: perbaiki tipe/form state dan konsistensi Navigation, segarkan tipe route sesuai prosedur Next yang dipakai, lalu jalankan pemeriksaan tipe dan build produksi. `npm run typecheck` untuk API sudah lulus pada audit ini.

**F02 — Origin link email tidak konsisten dengan lingkungan lokal. Status: konfigurasi lokal terkonfirmasi; perilaku fallback direproduksi.**

`PUBLIC_SITE_URL` tidak terisi pada lingkungan file lokal yang dibaca. Link email Lapidary menggunakan fallback `https://rendivirgo.com`; simulasi approval menghasilkan origin tersebut. Sementara itu `CustomerAuthService.appOrigin()` mengambil origin pertama dari `APP_ORIGIN`, yaitu `http://localhost:3001`. Probe GET menunjukkan login port 3000 merespons 200, sedangkan port 3001 tidak dapat dihubungi saat audit.

Dampak: jika API yang berjalan memakai konfigurasi yang sama, approval dari database lokal mengarahkan pelanggan ke produksi dan verifikasi akun mengarahkan ke port lokal yang tidak aktif. Token claim lokal tidak tersedia pada database produksi.

Rekomendasi: gunakan satu origin frontend kanonis untuk link Lapidary dan autentikasi. Pada dev, set keduanya ke origin dev aktif; pada produksi, set ke domain produksi. Pisahkan daftar origin CORS dari origin pembentuk link email. Tambahkan pemeriksaan startup/readiness. Environment tambahan yang disuntikkan ke proses API belum diperiksa, sehingga kesimpulan tentang runtime tetap perlu dikonfirmasi sebelum pengiriman nyata.

**F03 — Kesiapan email lokal belum terkonfirmasi. Status: konfigurasi file lokal belum lengkap.**

`RESEND_API_KEY` dan `EMAIL_FROM` tidak terisi pada environment yang dibaca dari `api/.env` beserta environment shell audit. `SESSION_SECRET` tersedia. Service email menentukan enabled berdasarkan adanya API key, dan outbox menolak enqueue jika email disabled; simulasi membuktikan respons 503. Perubahan status seperti Reviewing juga dapat memerlukan enqueue notifikasi dan ikut gagal jika provider tidak aktif.

Dampak: alur administrasi bisa berhenti sebelum approval; registrasi/verifikasi akun juga bergantung pada email. Ini adalah temuan kesiapan konfigurasi, bukan bukti bahwa proses API yang sudah berjalan pasti tidak menerima environment tambahan.

Rekomendasi: tampilkan status kesiapan provider di admin, pastikan sender/domain dan secret stabil, lalu lakukan uji email ke alamat pengujian milik tim. Jangan menyebut email sudah diterima pelanggan hanya karena enqueue atau provider menerima request.

**F04 — Pembatalan dapat menimpa invoice yang dibayar secara bersamaan. Status: direproduksi dengan interleaving terkontrol pada service sebenarnya.**

`updateRequest()` membaca request beserta invoice sebelum transaksi. Pemeriksaan larangan membatalkan invoice Paid memakai snapshot awal. Saat menyimpan, perubahan request dan invoice dilakukan berdasarkan ID tanpa pemeriksaan ulang status/versi. `markInvoicePaid()` juga membaca kondisi invoice sebelum transaksi.

Reproduksi di memori: proses pembatalan membaca invoice Awaiting Payment; proses lain diasumsikan menyelesaikan pembayaran sebelum transaksi pembatalan berjalan; pembatalan tetap mengubah request menjadi Cancelled dan invoice menjadi Void meskipun `paidAt` sudah terisi. Pengujian ini tidak mengubah database asli dan bukan stress test PostgreSQL.

Dampak: catatan pembayaran dan status pekerjaan dapat tidak konsisten ketika ada dua tab/admin atau operasi bersamaan.

Rekomendasi: periksa dan ubah status di dalam transaksi dengan row lock atau pembaruan bersyarat berdasarkan status/versi, lalu pastikan jumlah record yang berubah tepat satu. Terapkan pola yang sama untuk konfirmasi pembayaran, pembatalan, perubahan estimasi, serta penggantian bukti transfer. Tambahkan uji konkurensi terhadap database pengujian.

**5. Temuan P2 — memengaruhi kelancaran pekerjaan dan pemulihan kesalahan**

**F05 — Tracking link opsional pelanggan masih gagal ketika kosong. Status: direproduksi.**

`changeTracking()` menginisialisasi `trackingUrl: ""`, lalu `submitTracking()` mengirim seluruh form melalui `JSON.stringify(form)`. DTO memakai `@IsOptional()` dan `@IsUrl()`; string kosong tetap divalidasi sebagai URL. Simulasi membuktikan payload tanpa field URL diterima, sedangkan payload dengan URL `""` ditolak. Normalisasi `null` pada form admin yang baru diperbaiki lulus validator.

Rekomendasi: normalisasi URL opsional di form pelanggan dan di batas API. Terima kosong sebagai tidak ada link, tetap tolak URL nonkosong yang tidak valid. Uji kurir+resi tanpa URL pada dashboard pelanggan.

**F06 — Kurir dan resi dapat dihapus setelah Return Shipped. Status: direproduksi.**

Guard pengiriman memakai nilai input yang tidak kosong atau nilai lama. Akan tetapi, penyimpanan menerima string kosong dan mengubahnya menjadi null. Menyimpan ulang request Return Shipped dengan kurir/resi kosong lolos karena guard menggunakan data lama, kemudian data lama tersebut hilang.

Rekomendasi: validasi nilai akhir yang benar-benar akan disimpan. Setelah dispatch, kurir dan resi harus tetap ada; koreksi resi perlu dicatat dalam riwayat. Simulasi sudah menunjukkan request dapat tetap Return Shipped dengan dua field tersebut null.

**F07 — Email intake awal belum memiliki jaminan outbox/retry. Status: pemeriksaan implementasi.**

Pembuatan request memanggil `email.send()` langsung untuk admin dan pelanggan. Nilai `false` hasil pengiriman tidak diperiksa; request tetap merespons sukses. Berbeda dari email approval/progress/invoice, pengiriman awal tidak mempunyai job outbox dan status retry yang dapat diperiksa admin.

Rekomendasi: masukkan email tanda terima dan notifikasi admin ke outbox dalam transaksi pembuatan request. Request yang berhasil disimpan harus punya status notifikasi yang dapat diaudit. Jangan menafsirkan outbox kosong saat ini sebagai bukti bahwa email intake tidak pernah terkirim.

**F08 — Undangan akun kedaluwarsa tidak punya pemulihan langsung. Status: direproduksi sebagian dan dikonfirmasi dari endpoint yang tersedia.**

Claim token berlaku 30 hari dan hanya bisa dipakai akun terverifikasi dengan email yang sesuai. Ini pengaman yang baik. Namun, menyimpan ulang status Approved tanpa perubahan tidak memperpanjang token dan tidak mengirim approval baru. Tombol retry hanya menangani job Failed; email Sent telah dibersihkan payload-nya. Tidak tersedia aksi khusus menerbitkan ulang undangan akun.

Rekomendasi: tambah aksi admin “Kirim ulang undangan akun” untuk request yang belum terhubung, dengan token baru, pembatasan frekuensi, audit log, dan penanganan undangan lama. Mengubah nilai estimasi untuk memicu undangan bukan prosedur pemulihan yang layak.

**F09 — Cancelled setelah material diterima tidak memiliki alur pengembalian bahan. Status: gap operasional terkonfirmasi.**

Material Received dan In Progress dapat berubah menjadi Cancelled; Cancelled merupakan status terminal. Alur kirim kembali normal mensyaratkan invoice Paid dari pekerjaan Completed. Tidak ada jalur khusus mengembalikan batu yang sudah dititipkan ketika pekerjaan dibatalkan.

Rekomendasi: pisahkan status pekerjaan dari status penguasaan/pengembalian material. Catat bahan yang sudah diterima, alasan pembatalan, biaya yang disetujui, ongkir pengembalian, kurir/resi, dan penerimaan pelanggan sampai material kembali. Tutup proyek setelah kewajiban pengembalian selesai.

**F10 — Koreksi invoice/alamat dan revisi biaya setelah Completed belum ditangani. Status: gap operasional dari kode.**

Snapshot alamat pada invoice mencegah perubahan profil mengubah tujuan pengiriman secara diam-diam. Namun, belum ada aksi admin khusus memperbaiki alamat dan ongkir pada invoice yang belum dibayar. Ketika biaya final melebihi maksimum, pesan meminta estimasi baru, sementara status Completed tidak memiliki transisi ke Estimate Sent dan perubahan estimasi pada Completed diblokir.

Rekomendasi: sediakan prosedur invoice revisi sebelum dibayar dengan alasan, versi, pemberitahuan, dan persetujuan yang jelas. Untuk kenaikan maksimum jasa, minta persetujuan baru sebelum pekerjaan tambahan; tampilan admin sebaiknya menjelaskan bahwa dari Completed saat ini biaya harus tetap berada dalam batas yang telah disetujui. Invoice yang sudah dibayar memerlukan proses penyesuaian tersendiri.
